0. HOW TO USE THIS FILE
======================================================================

Use this file as the single implementation brief for building MINO from an empty repository to a tested, deployable web application. Give the full file to the coding agent or development team at the beginning. Then implement the numbered phases in order. Do not try to implement every phase in one giant code change.

This document combines three different kinds of information:

A. SOURCE-PAPER REQUIREMENTS
   Requirements directly represented in the uploaded paper, "Deepfake Detection: A Systematic Literature Review" (October 2024 issue). The paper reviews 112 studies published from 2018 through 2020. It classifies approaches into deep learning, classical machine learning, statistical, and blockchain-based methods. Its architecture and module descriptions specify a Service Provider/Admin and Remote User workflow.

B. VERIFIED EXTERNAL RESEARCH
   Findings from current research repositories, benchmark papers, dataset maintainers, security guidance, and the C2PA specification available on 16 November 2026. These are used to modernize the older paper.

C. ENGINEERING RECOMMENDATIONS
   Proposed architecture, features, implementation order, database design, API design, and acceptance criteria. These are a practical implementation plan, not claims that the supplied paper already implemented them.

IMPORTANT PRODUCT LIMITATION
MINO must not claim that it can prove a video is real or fake with certainty. It is a probabilistic forensic screening system. Its result must communicate uncertainty, model version, supported media type, and known limitations. A model score is not proof, and a high score is not a legal conclusion.

1. SOURCE PAPER ANALYSIS - WHAT MUST BE PRESERVED
======================================================================

1.1 Research foundation

The supplied paper reviews 112 research articles from 2018 to 2020. Its four technique categories are:
- Deep learning-based techniques.
- Classical machine learning-based techniques.
- Statistical techniques.
- Blockchain-based techniques.

The paper reports that deep-learning methods, especially CNN-oriented approaches in the reviewed literature, generally outperform non-deep-learning approaches. It also notes that results depend on the dataset, selected features, and how training and testing data are split. It warns that performance on unrelated datasets can fall substantially.

This review period is historical. Do not present the paper's 2018-2020 survey as a complete account of 2026 research. Use it as the project's academic foundation, then use the modern research section in this brief for implementation decisions.

1.2 Original architecture shown in the paper

The system architecture diagram on PDF page 4 depicts:
- A Web Server.
- A Web Database used to store and retrieve information.
- A Service Provider module.
- A Remote User module.
- Information and dataset-result exchange between the server, database, and service provider.
- Remote-user registration/login, deepfake prediction, and profile viewing.

1.3 Original Service Provider/Admin functions

Preserve these functions in MINO:
- Secure service-provider login.
- Train and test datasets.
- View video datasets used for training and testing.
- View accuracy in bar charts.
- View detailed training/testing accuracy results.
- View prediction types.
- View prediction ratios.
- Download prediction-result datasets.
- View prediction-ratio results.
- View remote users.

1.4 Original Remote User functions

Preserve these functions in MINO:

- Submit media for deepfake prediction.
- View prediction type/result.
- View and update a profile.

1.5 Original research and limitations to retain in the project report

The paper discusses biological/physiological signals, facial landmarks, 3D head pose, visual artifacts, MLP/CNN methods, Meso-4 and MesoInception-4, GAN-related traces, and blockchain/IPFS/ENS concepts. Treat these as research directions, not as already implemented MINO features.

The paper mentions an accuracy figure as high as 98% for some methods but also explains that performance depends on dataset and feature selection. Do not use 98% as MINO's advertised accuracy. MINO must publish its own reproducible evaluation results, including false-positive and cross-dataset performance.

2. PRODUCT VISION AND SCOPE
======================================================================

2.1 Product definition

MINO is a web-based media-forensics platform that allows an authenticated user to submit an image or video, runs supported deepfake-detection models, and returns a transparent analysis report. An administrator manages users, datasets, model versions, training/evaluation runs, and system-wide analytics.

2.2 Primary objective

Build a practical, explainable, privacy-conscious deepfake screening platform with:
- User registration, login, profile, and analysis history.
- Secure image/video upload.
- Background processing for time-consuming video analysis.
- A model-inference pipeline that can be upgraded without rewriting the application.
- Video-level and frame-level results.
- An admin dashboard for dataset/model operations and analytics.
- Reproducible model evaluation and documented limitations.

2.3 Initial supported media

MVP:
- Images: JPG/JPEG, PNG, WEBP.
- Videos: MP4, MOV, WEBM, subject to the installed FFmpeg/FFprobe build and codec support.
- Face-manipulation detection is the first supported detection task.
- General synthetic-image detection is a separately versioned task and must not be implied by a face-swap model.

Later extensions:
- Audio deepfake detection.
- Audio-video synchronization and cross-modal consistency analysis.
- C2PA Content Credentials validation.
- Optional integrity anchoring for hashes.

Do not claim that MVP supports every social-media format, every generated image, every audio format, or live-stream detection.

2.4 User roles

REMOTE USER
- Register, verify email, sign in, sign out, reset password.
- View and edit permitted profile details.
- Upload supported images/videos.
- View upload and analysis progress.
- View a result, frame timeline, supported evidence, and model details.
- View analysis history.
- Download an analysis report.
- Delete an uploaded asset and its analysis data, subject to documented retention/audit obligations.

ADMIN / SERVICE PROVIDER
- Secure admin login and role-based access.
- Approve, suspend, reactivate, or remove users.
- View user and service statistics.
- Inspect dataset registrations and dataset versions.
- Start/monitor training and evaluation jobs.
- Compare model versions and evaluation metrics.
- Activate, stage, rollback, or retire a model version.
- Review analysis outcomes and system errors without exposing unnecessary user media.
- Export aggregate prediction/evaluation data as CSV/JSON.
- View audit logs and system health.

OPTIONAL RESEARCHER ROLE (later)
- Access approved research datasets and experiment reports.
- Create training/evaluation runs without admin-level user-management access.
- Cannot activate a production model unless explicitly granted permission.

3. MODERN RESEARCH FINDINGS AND DESIGN CONSEQUENCES
======================================================================

3.1 Generalization is a core engineering requirement

A detector can perform well on one dataset and fail on new sources, codecs, compression levels, identities, or manipulation types. Meta's DFDC page reports that leaderboard rankings changed significantly between the public set and the black-box set. DF40 (NeurIPS 2024) explicitly identifies forgery diversity, realism, and narrow evaluation protocols as reasons current detector results can fail to generalize.

Design consequence:
- Never rely on one random train/test split from one dataset.
- Split by source video and, where possible, identity/subject to avoid leakage.
- Evaluate on at least one dataset not used for training.
- Record per-dataset and per-manipulation metrics.
- Include compression, resizing, blur, noise, and frame-rate changes in robustness evaluation.
- Display the model version and supported task in every user-facing result.

3.2 DeepfakeBench as a benchmark reference

The current DeepfakeBench-v2 repository advertises 36 detection methods: 28 image detectors and 8 video detectors. Its listed methods span naive CNNs, spatial approaches, frequency approaches, and video/temporal approaches. Examples include Xception, MesoNet, EfficientNet-B4, Face X-ray, F3Net, TALL, I3D, FTCN, X-CLIP, and VideoMAE. Its listed metrics include frame-level AUC, video-level AUC, accuracy, equal error rate, precision-recall, and average precision. The repository also references newer methods including LSDA and an ICML 2025 Spotlight method called Effort.

Design consequence:
- Use DeepfakeBench as a research/benchmark reference and a possible offline comparison environment.
- Do not attempt to integrate all 36 detectors into the production web app at the beginning.
- Start with one reproducible baseline model behind a detector interface.
- Add another detector only when its license, weights, compute requirements, and validation results are understood.
- Record all preprocessing settings so comparisons are fair.
- Check the exact license of the repository, each model, each checkpoint, and each dataset before reusing them.

3.3 Dataset selection

Recommended dataset strategy:

A. FaceForensics++ (FF++)
- Useful foundational dataset containing original video sequences and manipulated versions made using several face manipulation approaches.
- Access is controlled; the official repository asks users to complete an access form and receive download access.
- Keep the dataset out of the source repository. Follow the official terms and access process.

B. Celeb-DF
- Useful for testing higher-quality celebrity face-swap examples.
- The CVPR paper describes 5,639 high-quality DeepFake videos.
- Review the official terms and access requirements before use.

C. DFDC
- Meta describes a preview set of about 5,000 videos and a full dataset of about 124,000 videos using multiple manipulation algorithms.
- Full dataset access has AWS account/IAM prerequisites according to the official page.
- Its public-versus-black-box results are a useful warning about overfitting to a benchmark.

D. DeeperForensics-1.0
- The project describes 48,475 source videos and 11,000 manipulated videos, with multiple real-world perturbations.
- Its stated storage requirement is roughly 284 GB; plan storage before attempting to download it.
- Access requires accepting the dataset terms and requesting access.

E. WildDeepfake
- Collected from web videos and intended to represent more in-the-wild conditions.
- The maintainers describe restricted research use and an applicant verification process.
- Do not assume public/commercial redistribution rights.

F. DF40
- NeurIPS 2024 benchmark with 40 distinct deepfake techniques.
- Especially relevant for testing a detector against a wider range of newer methods rather than only older face swaps.
- Verify current access terms, storage needs, and suitability before downloading.

Dataset rules:
- Read and record each dataset's licence/terms before use.
- Keep a `DATASET_MANIFEST.csv` with source, version, access date, terms URL, labels, split, and checksum where permitted.
- Do not push datasets, face crops, videos, credentials, or private data to GitHub.
- Never mix frames of the same source video or subject across train and test splits in a way that leaks identity/source information.
- Keep a small synthetic test fixture only if its licence and consent permit repository use.
- For tests, generate tiny synthetic media fixtures or use mocks; do not commit research datasets.

3.4 Recommended model strategy

MVP baseline:
- A face-focused binary image classifier using a maintainable pretrained CNN backbone such as EfficientNet-B0 or Xception, fine-tuned on approved face-manipulation data.
- For a lightweight first deployment, benchmark EfficientNet-B0 or another smaller backbone on CPU. Use Xception as a research baseline if the implementation/weights and compute are appropriate.
- Keep model loading, preprocessing, inference, and post-processing behind a common interface, so models can be exchanged later.

Video MVP:
- Decode the video safely with FFmpeg/FFprobe.
- Sample a configurable number of frames at evenly distributed timestamps (for example, 16 frames for a first pass; make this configurable).
- Detect and crop face regions from the sampled frames.
- Run the frame detector on valid face crops.
- Aggregate frame scores using an aggregation method selected on validation data (compare mean, median, and top-k mean; do not assume one is universally best).
- Return a video-level result plus a timestamped frame-risk timeline.

Later research models:
- Temporal/video detectors such as FTCN, TALL, I3D, X-CLIP, or VideoMAE.
- Frequency-aware methods such as F3Net or SPSL.
- Generalization-oriented methods such as LSDA and other methods currently benchmarked by DeepfakeBench.
- These are research candidates, not guaranteed drop-in upgrades. Reproduce their preprocessing and evaluate independently.

Audio and multimodal (future phase):
- Add a separate audio spoof/deepfake detector with its own datasets, labels, metrics, and model version.
- Add an audio-video consistency model only after both branches have been independently evaluated.
- Never infer audio authenticity from a video-only classifier.
- If audio is not enabled, clearly label it "not analyzed".

3.5 Calibration and user-facing classes

Store a continuous estimated manipulation score from 0.0 to 1.0. Calibrate the score on a held-out validation set where practical. Define thresholds from validation data and version the thresholds with the model.

Recommended UI labels:
- LIKELY MANIPULATED: score is above the validated high threshold.
- INCONCLUSIVE: score lies in the uncertain band, no usable face was found, the media quality is insufficient, or the media is outside the supported domain.
- LIKELY AUTHENTIC: score is below the validated low threshold.

The interface must say "model-estimated manipulation likelihood" and must not say "verified real" or "100% fake". A heatmap/attention map is a model visualization, not proof of the exact manipulated pixels.

3.6 Evaluation metrics

Minimum model report:
- ROC-AUC.
- PR-AUC / Average Precision.
- Precision, recall, F1.
- Balanced accuracy.
- Confusion matrix.
- False-positive rate and false-negative rate.
- Equal Error Rate (EER), where appropriate.
- Frame-level AUC and video-level AUC.
- Per-dataset and per-manipulation metrics.
- Calibration metrics (for example, Brier score or ECE) when score calibration is implemented.
- Inference latency, memory consumption, and supported input range.

A single accuracy percentage is not enough. Always show the test dataset, split strategy, sample count, date, model version, and threshold used.

3.7 C2PA provenance is separate from detection

The C2PA 2.5 specification (October 2026) defines cryptographically verifiable provenance information, including signed assertions and asset bindings. It can help validate whether provenance claims are associated with an asset and have not been tampered with. C2PA explicitly does not make a value judgement that the provenance is "good" or "bad" and does not establish whether the depicted content is factually true.

Design consequence:
- Add a separate optional provenance panel: "C2PA credentials found / not found / invalid / unsupported".
- Do not treat missing C2PA metadata as evidence that a file is fake.
- Do not treat valid C2PA metadata as proof that the content is truthful or unmanipulated.
- Keep provenance validation separate from the ML manipulation score.

3.8 Blockchain/IPFS decision

The supplied paper discusses blockchain, IPFS, and Ethereum Name Service concepts. Preserve the idea only as an optional integrity/provenance extension:
- Always calculate a SHA-256 hash for each uploaded asset.
- Store the hash, timestamp, uploader reference, and model/report hash in the database audit trail.
- A later extension may anchor hashes or signed report references to a permissioned ledger or test network.
- Never store raw private videos, face crops, passwords, or personal data on a public blockchain.
- Do not use blockchain as a deepfake classifier; a blockchain can preserve a record or prove that bytes match a hash, not determine whether the depicted event is real.
- IPFS is not automatically private. Use private object storage for user uploads unless a deliberate access-controlled architecture is designed.

4. COMPLETE FEATURE REQUIREMENTS
======================================================================

4.1 Authentication and account management
- Email/password registration.
- Email verification.
- Secure password hashing (Argon2id or a maintained equivalent).
- Login/logout.
- Short-lived access tokens and rotating refresh tokens, or secure server sessions.
- Password reset flow using single-use expiring tokens.
- Role-based access control (RBAC).
- Optional admin approval workflow matching the paper.
- Account status: pending, active, suspended, deleted.
- Profile display/edit.
- Account deletion request.
- Login rate limiting and audit events.

4.2 Media ingestion
- Drag-and-drop upload and file picker.
- Upload progress and clear error messages.
- Allowlisted image/video formats only.
- Configurable maximum file size and video duration.
- Validate file extension, MIME type, and file signature; do not trust browser-supplied MIME type alone.
- Generate server-side UUID filenames; never use a client filename as a storage path.
- Calculate SHA-256 hash.
- Read media metadata safely.
- Store media privately outside the web root.
- Provide explicit consent/notice before analysis.
- Delete original files according to the retention policy.

4.3 Image analysis
- Validate image dimensions, encoding, and size.
- Detect whether an appropriate face region exists for the selected model.
- Run the face-focused classifier.
- Return score, class, model version, processing time, and quality/coverage status.
- Show a visual explanation only if that method is implemented and documented.
- Do not claim a face-swap model detects all AI-generated or edited images.

4.4 Video analysis
- Validate container and codecs using a safe FFprobe call.
- Reject or mark unsupported videos cleanly.
- Enforce duration, resolution, file size, frame-count, and timeout limits.
- Extract sampled frames with FFmpeg.
- Detect face regions without identifying the person.
- Run frame-level inference.
- Aggregate frame scores to a video-level estimate.
- Store timestamped frame scores.
- Show a timeline with high-risk timestamps.
- Show number of sampled frames and number of valid face frames.
- Provide a low-quality/insufficient-evidence state.
- Clean temporary frame files after processing.

4.5 Analysis result and report
- Clear result label and estimated manipulation score.
- Explanation that the score is probabilistic.
- Model name, model version, model task, threshold version, and analysis timestamp.
- Frame timeline and selected suspicious timestamps.
- Uploaded media summary (type, dimensions, duration, size).
- Optional C2PA status in a separate section.
- SHA-256 file hash.
- Downloadable PDF report (later phase) and JSON result export.
- Report includes limitations and evaluation provenance, not only a percentage.

4.6 User dashboard and history
- Total analyses.
- Recent analyses and statuses.
- Search/filter by date, file type, and result class.
- Open previous result.
- Delete an analysis and associated media.
- Pagination; do not load the entire history at once.

4.7 Admin dashboard
- Total users, active users, pending approvals.
- Total media analyses, completed/failed/queued jobs.
- Breakdown by prediction class.
- Daily/weekly analysis volume.
- Average inference duration and failure rate.
- Charts with clearly labelled date range and sample counts.
- Dataset registry and dataset usage summary.
- Training/evaluation run summary.
- Model version comparison.
- User approval/suspension.
- CSV/JSON export of aggregate results.
- Audit log and health status.

4.8 Dataset management
- Register dataset metadata; do not upload large datasets through normal user upload endpoints.
- Track dataset name, source URL, version, licence/terms, labels, checksums, access date, and permitted use.
- Track preprocessing version and split manifest.
- Store dataset files on a research storage volume or approved object store.
- Admin-only operations for dataset validation and indexing.

4.9 Model registry and training management
- Track architecture and model version.
- Track checkpoint location and SHA-256 checksum.
- Track training dataset versions and split IDs.
- Track hyperparameters, preprocessing, code commit SHA, random seed, training date, and hardware.
- Track metrics and evaluation report location.
- Model states: draft, training, evaluated, staged, active, retired, failed.
- Require evaluation approval before activating a production model.
- Support rollback to a known model version.
- Keep production inference pinned to a model version for each analysis.

4.10 Privacy, safety, and governance
- Private media by default.
- Only the owner and explicitly authorized staff can access media.
- Retention settings and deletion workflow.
- Consent and acceptable-use policy.
- No face recognition or identity lookup in the MVP.
- No public gallery of uploaded videos.
- Do not expose face crops or original URLs in public logs.
- Redact personal data from logs.
- Provide an abuse reporting/contact path.
- Provide result disclaimers and a means to report a potentially incorrect result.

8. DATABASE DESIGN
======================================================================

Use PostgreSQL UUID primary keys, UTC timestamps, foreign keys, indexes, migrations, and explicit status enums. Store large media files and model checkpoints in private object storage, not as database blobs.

8.1 users
- id (UUID, primary key)
- email (unique, normalized)
- password_hash
- full_name
- role (USER, ADMIN, optional RESEARCHER)
- status (PENDING, ACTIVE, SUSPENDED, DELETED)
- email_verified_at
- created_at, updated_at, last_login_at

8.2 media_assets
- id
- owner_user_id
- storage_key (private storage object key)
- original_filename (display value only; never used as path)
- detected_mime_type
- media_type (IMAGE, VIDEO, AUDIO_FUTURE)
- file_size_bytes
- sha256
- width, height, duration_seconds, codec, frame_rate (nullable as appropriate)
- retention_expires_at
- created_at, deleted_at

8.3 analysis_jobs
- id
- owner_user_id
- media_asset_id
- status (QUEUED, PROCESSING, COMPLETED, FAILED, CANCELLED)
- progress_percent
- model_version_id
- task_type (FACE_DEEPFAKE_IMAGE, FACE_DEEPFAKE_VIDEO, later task types)
- error_code (safe machine-readable code)
- error_message (sanitized)
- queued_at, started_at, completed_at

8.4 analysis_results
- id
- analysis_job_id (unique or one-to-one as appropriate)

9. MACHINE-LEARNING IMPLEMENTATION SPECIFICATION
======================================================================

9.1 Dataset manifest format

Use CSV or Parquet with at least:
- sample_id
- media_path (local research path or object key)
- label (REAL=0, FAKE=1)
- dataset_name
- dataset_version
- manipulation_type
- source_video_id
- subject_id / identity_id where permitted
- split (TRAIN, VALIDATION, TEST, CROSS_DATASET_TEST)
- license/permission reference
- checksum

The manifest should be the reproducibility contract. Never infer labels from filenames alone without validating them against the dataset's authoritative labels.

9.2 Splitting policy

- Split at source-video level.
- Keep all frames/crops from a video in one split.
- Where possible, keep subjects/identities disjoint between train and test.
- Keep a validation set for threshold selection and calibration.
- Keep a final untouched test set.
- Add cross-dataset evaluation: train on selected datasets and test on a dataset/manipulation family not used for training.
- Record the exact split manifest and checksum for each experiment.

9.3 Preprocessing pipeline

Image:
1. Read the file with a safe image decoder.
2. Normalize EXIF orientation.
3. Validate dimensions and color channels.
4. Detect face regions for the face-focused model.
5. Crop/align faces using documented coordinates and interpolation.
6. Resize and normalize exactly as required by the checkpoint.
7. Preserve enough metadata to reproduce the transform.

Video:
1. Inspect container, stream, duration, dimensions, frame rate, and codec using FFprobe.
2. Enforce duration, resolution, size, and processing time limits.
3. Sample frames at fixed/evenly distributed timestamps or a documented sampling method.
4. Detect face boxes on sampled frames.
5. Optionally track faces across frames; do not perform identity recognition.
6. Crop/align valid faces and apply the exact training transform.
7. Run frame inference.
8. Aggregate only valid frame outputs.
9. Store timestamped scores and summary statistics.
10. Delete temporary files even if the job fails.

9.4 Augmentation policy

Use realistic augmentations and document their probabilities:
- JPEG/video compression and re-encoding.
- Resize and downsample/upsample.
- Mild blur and sharpening.
- Brightness, contrast, saturation, and color shifts.
- Sensor/compression noise.
- Cropping and partial occlusion.
- Frame-rate changes and frame dropping for video.

Do not use augmentations that destroy the forensic signal or create label leakage. Compare experiments with a fixed validation protocol.

9.5 Baseline training

- Implement one baseline classifier first.
- Use pretrained image weights where licence permits.
- Replace the classification head with two classes.
- Use class weighting or a sampler if class imbalance is present.
- Record optimizer, learning rate, batch size, epochs, scheduler, seed, image size, augmentations, dataset versions, and checkpoint hash.
- Save best checkpoint based on a validation metric selected before training (for example, validation AUC), not test performance.
- Save training curves and a complete configuration file.
- Never select the production threshold by looking at the final test set.

9.6 Video-level aggregation

Compare at least:
- Mean frame probability.
- Median frame probability.
- Top-k mean of the highest-risk valid frames.

Choose the aggregation policy using validation data and evaluate it on a separate test set. Store the aggregation name/version with every result. If a temporal model is implemented later, compare it against the frame-aggregation baseline.

9.7 Training/evaluation deliverables

Every training run must produce:
- Config file.
- Dataset/split manifest reference.
- Code commit SHA.
- Training log.
- Validation curves.
- Confusion matrix.
- ROC and precision-recall curves.
- Per-dataset/per-manipulation table.
- Frame-level and video-level metrics.
- Calibration/threshold report.
- Checkpoint and SHA-256 checksum.
- Model card describing intended use, non-intended use, known limitations, data, and evaluation.

9.8 Model serving

- Define a `Detector` interface with `load()`, `predict_image()`, `predict_video_frames()` or equivalent, `metadata()`, and `health_check()`.
- Load the active model once per worker process; do not reload weights per frame/request.
- Keep inference deterministic where possible.
- Support CPU execution as the default development path.
- Benchmark PyTorch inference against ONNX Runtime if exporting to ONNX.
- If using quantization, compare quality metrics before/after and document the trade-off.
- Use bounded worker concurrency to protect CPU/RAM.
- Record latency and memory usage.

12. SECURITY, PRIVACY, AND RELIABILITY
======================================================================

12.1 File-upload protection

Follow defense-in-depth principles from the OWASP File Upload Cheat Sheet:
- Allowlist only required file extensions.
- Normalize/validate filenames and generate random server-side storage names.
- Do not trust the browser's Content-Type header.
- Check MIME type and file signature together; neither alone is sufficient.
- Enforce file-size, duration, resolution, frame-count, and decompression limits.
- Store uploads outside the web root/private object storage.
- Require authentication and ownership checks.
- Do not make uploaded media public by default.
- Scan/parse in a worker with process and time limits.

12.2 FFmpeg/FFprobe safety
- Invoke binaries with argument arrays, not shell string concatenation.
- Never interpolate user filenames into a shell command.
- Use a generated temporary directory per job.
- Set execution timeout, CPU/memory limits, and output limits.
- Use a patched FFmpeg build.
- Restrict protocols and network access where possible.
- Reject path traversal and unexpected file references.
- Clean up temporary data in a `finally`/job-cleanup path.

12.3 Authentication and authorization
- Hash passwords with Argon2id or a maintained secure password hashing implementation.
- Use secure, HttpOnly, SameSite cookies if using cookie-based refresh sessions.
- Protect state-changing requests from CSRF when cookie-based authentication is used.
- Enforce role and owner checks on the backend; frontend route guards are not security.
- Rate-limit login, password reset, registration, and upload/analysis creation.
- Use email verification and secure reset tokens.
- Audit admin actions.

12.4 Secrets and deployment
- Keep secrets in environment variables or a secrets manager.
- Commit `.env.example`, never real `.env` files.
- Rotate exposed credentials immediately.
- Use HTTPS in deployment.
- Restrict CORS to known frontend origins.
- Restrict database and Redis network access.
- Keep dependencies pinned/locked and scan for vulnerabilities.

12.5 Privacy
- Explain why the media is processed and how long it is retained.
- Use private object storage and short-lived signed URLs.
- Minimize logs; do not log file contents, raw face crops, tokens, or personal data.
- Give users a deletion flow.
- Specify backup deletion limitations honestly.
- Define an admin access policy and audit staff access.
- Do not perform face identification or match users to external identities.

12.6 Reliability and observability
- Structured JSON logs with request/job IDs.
- Worker heartbeat and queue depth monitoring.
- Health endpoints: `/health/live` and `/health/ready`.
- Distinguish liveness from readiness (database/model/storage dependencies).
- Retry only transient failures and use bounded retries.
- Make job processing idempotent where possible.
- Keep a dead-letter/failed-job review path.
- Track inference latency, worker memory, queue wait, and processing failures.

18. PERFORMANCE TARGETS - MEASURE, DO NOT INVENT
======================================================================

Set initial operational targets after measuring the selected model and host. Do not publish fabricated benchmark numbers.

Measure:
- Upload throughput and maximum supported file size.
- Queue wait time.
- Video decode time.
- Face detection time.
- Model inference time per frame.

- Peak RAM and CPU usage.

- API p50/p95 latency excluding asynchronous inference.

Treat these as configurable starting limits, not universal performance claims. Adjust only after load testing and security review.

19. RISKS AND MITIGATIONS
======================================================================

Risk: High in-dataset score but poor real-world detection.
Mitigation: source/identity-disjoint splits, cross-dataset tests, DF40/modern manipulation evaluation, model card, conservative labels.

Risk: User assumes result is proof.
Mitigation: clear probability language, uncertainty state, limitations, and report disclaimer.

Risk: Malicious media file attacks the decoder.
Mitigation: allowlists, signatures, isolated worker, FFmpeg timeouts, resource limits, patched dependencies, private storage.

Risk: Dataset licence or consent violation.
Mitigation: terms review, dataset register, no redistribution, no repository upload, documented retention.

Risk: GPU/hosting cost or free-tier limitations.
Mitigation: CPU-capable fallback, asynchronous queue, configurable sampling, measured limits, local Docker development, separate training environment.

Risk: Model upgrade silently changes old results.
Mitigation: pin model version per job/result, store checkpoint checksum, immutable report metadata, rollback.

Risk: C2PA confusion.
Mitigation: separate provenance panel and ML result; missing credentials do not equal fake; valid provenance does not equal truth.

Risk: Blockchain adds complexity and leaks data.
Mitigation: make it optional, anchor hashes only, never upload media/personal data, do not depend on it for inference.

Risk: Inference queue overload.
Mitigation: maximum file length/size, worker concurrency cap, per-user rate limit, queue monitoring, quotas.
